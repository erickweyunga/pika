# tree-sitter-pika

A [tree-sitter](https://tree-sitter.github.io) grammar for Pika, used by the Zed extension in
[`../zed`](../zed) for syntax highlighting, the outline, indentation and text objects.

It follows the reference parser in `crates/pika_syntax` (section 16 of the specification). It
accepts some programs that the reference parser reports errors for, such as chained comparisons,
and recovers from errors locally, so that the rest of a file keeps its highlighting while you
type. It is stricter in one place: the named arguments of built-in forms must come in the order
the specification writes them (`do=` before `else=`, `in=` before `do=`, and `do=` last in
`:for`).

## Layout

| Path | Contents |
|---|---|
| `grammar.js` | the grammar |
| `src/scanner.c` | the external scanner: line breaks that end statements, `name=` of named arguments, string text and raw strings |
| `src/parser.c`, `src/grammar.json`, `src/node-types.json`, `src/tree_sitter/` | generated by `tree-sitter generate`; never edit them by hand |
| `test/corpus` | syntax tree tests |
| `test/highlight` | highlighting tests, run against `../zed/languages/pika/highlights.scm` |
| `bindings/rust` | the Rust crate `tree-sitter-pika`, and its tests |

## How the grammar handles Pika's lexical rules

- **Joined tokens** (section 3.3). Where the reference parser requires a token to be joined to
  the one before it, the grammar uses `token.immediate`: the `:` of `x:i64`, the `<` of `List<T>`,
  the `{` of `Point{...}`, the `->` of `$p->x`, the `?` of `T?`, the `/` between path segments,
  and the `=` of `name=value`. So a spaced `->` is a return type, and a spaced `<` a comparison.
- **Line breaks** (section 3.4). The external scanner produces a line-break token only where the
  grammar accepts one: inside blocks, bodies and collection literals, and at the top level.
  Everywhere else, such as inside `( )`, `[ ]` and `< >`, line breaks are whitespace.
- **Named arguments.** `name=` is recognized by the scanner, which looks at the `=` after the
  name. The arguments of the built-in forms (`do=`, `else=`, `from=`, `in=`, ...) are keywords of
  the grammar instead, since they decide how the value is parsed: `do={...}` is a block, while a
  `{...}` argument of an ordinary command is a collection literal.

## Development

Requires the [tree-sitter CLI](https://tree-sitter.github.io/tree-sitter/creating-parsers/1-getting-started.html),
the version in `.github/workflows/ci.yml`, and Node.js.

```sh
cd editors/tree-sitter-pika
tree-sitter generate                 # regenerate src/ after changing grammar.js
tree-sitter test                     # corpus and highlighting tests
tree-sitter test --update            # rewrite the expected trees; review the changes
tree-sitter parse path/to/file.pk    # print the syntax tree of a file
cargo test -p tree-sitter-pika       # the checks below
```

`cargo test -p tree-sitter-pika` checks that:

- every `.pk` file in the repository that the reference parser accepts, and every `pika` example
  in the specification, parses without errors
- random programs built from those files' lines parse without errors whenever the reference
  parser accepts them, and any input parses without hanging or crashing
- the Zed queries compile against the grammar and use captures that Zed knows
- the Zed manifests refer to this grammar

Commit the regenerated `src/` with every change to `grammar.js`; CI checks that it is up to date
and that the grammar compiles to WebAssembly with the wasi-sdk that Zed uses.
